# Коллекция математических подходов для объяснения решений

## Vision
Объясняя решение задачи человеку, называть не формулу, а идею за ней — так, чтобы по признакам в
условии следующей задачи ту же идею можно было узнать заранее. Коллекция копится по мере разбора
решённых задач, но сама коллекция НЕ хранит ни одной задачи и ни одной ссылки на задачу — только
чистые идеи, как в учебнике. Связь с тем, где идея применена, идёт в одну сторону: задача сама
ссылается на нужный ей блок здесь по имени; обратного индекса «где применялось» коллекция не
ведёт (см. MUST-no-task-specifics). Связана с каталогом картинок: у каждой идеи, у которой есть
устоявшийся визуальный образ, есть чем её показать — но не у каждой такой образ обязан
существовать.

## Термины
MUST/MUST NOT/SHALL/SHOULD/SHOULD NOT/MAY — как в RFC 2119. Термины — `_terms.md`, контекст
`approach`: [approach::Collection](../_terms.md#approachcollection),
[approach::InclusionExclusion](../_terms.md#approachinclusionexclusion),
[approach::VennDiagram](../_terms.md#approachvenndiagram),
[approach::ArithmeticProgressionSum](../_terms.md#approacharithmeticprogressionsum),
[approach::Precomputation](../_terms.md#approachprecomputation),
[approach::BinarySearch](../_terms.md#approachbinarysearch),
[approach::TrialDivision](../_terms.md#approachtrialdivision).

## Скоуп
**В скоупе:** блоки `[approach::*]` в `memory-bank/_terms.md`, схема записи, двусторонняя связь с
[visualizations](visualizations.md), дисциплина пополнения, дисциплина «атом или композиция».

**Вне скоупа:** `TRICKS.md` в корне репозитория — приёмы УСКОРЕНИЯ вычисления, найденные в
исследовательском процессе, со своей цитатной дисциплиной; здесь — идеи, которые стоит
проговорить при объяснении, независимо от того, ускоряют они что-то или нет. Сами картинки —
[visualizations](visualizations.md). Сами задачи (условие, решение, критерии корректности) —
живут в `euler{NNN}/README.md`, не здесь (см. MUST-no-task-specifics).

## Находки, положенные в основу
- **F1** Коллекция подходов и каталог картинок существовали параллельно без ссылок; при связывании
  выяснилось: подходов без картинки нет, а картинка без подхода одна (счёт прыжками —
  понятие, не способ счёта). Трассировка: MUST-visualized-by, MUST-no-invented-approach.
- **F2** Первая формулировка включения-исключения была «А+Б−АБ» — частный случай двух условий,
  выданный за общий. Трассировка: MUST-general-case.
- **F3** (euler002) Признак подхода «предвычислить один раз + бинарный поиск на запрос» легко
  спутать с самим предвычислением — предвычисление ничем не отличается от общего «сначала
  посчитай, потом используй» и не тянет на отдельную визуализацию (тот же класс, что счёт
  прыжками для «кратно», F1); отдельная, безусловно стандартная техника — сам бинарный поиск.
  Трассировка: MUST-visualized-by, MUST-no-invented-approach.
- **F4** (euler002, найдено прямым вопросом пользователя «точно по 1 подходу?») F3 смешала два
  разных вопроса — «нужна ли этому шагу отдельная КАРТИНКА» (нет — предвычисление не рисуется, F1)
  и «нужна ли этому шагу отдельная ЗАПИСЬ ПОДХОДА» (это не то же самое: у обеих идей задачи 1 —
  включение-исключение и сумма прогрессии — своя литература, они узнаются в разных задачах порознь;
  предвычисление и бинарный поиск — тоже: их можно узнать порознь в других задачах, только у
  предвычисления нет своего визуального образа). Единый блок `PrecomputeAndBinarySearch` был
  неверно слеплен из-за этой путаницы. Разделён на [approach::Precomputation](../_terms.md#approachprecomputation)
  (без картинки — честно помечено, не выдумано) и [approach::BinarySearch](../_terms.md#approachbinarysearch)
  (с картинкой). Трассировка: MUST-approach-independent-of-picture.
- **F5** (прямой запрос пользователя: «1 подход — 1 картинка», «мемори-банк не должен содержать
  конкретные задачи», «должны быть ссылки на стандартные подходы»). Три независимых, но связанных
  находки одним проходом:
  1. `[approach::InclusionExclusion]` нарушала новое правило «1 картинка на подход» — имела ДВЕ
     (полоска и диаграмма Венна). Разбор показал, что это НЕ одна идея дважды нарисованная, а две
     разные, независимо стандартные идеи, которые часто используются вместе (тот же паттерн, что
     F4): включение-исключение — арифметика подсчёта; диаграмма Венна — представление логических
     утверждений кругами, изобретена Джоном Венном в 1880 для СОВСЕМ ДРУГОЙ цели (не для счёта).
     Разделены на [approach::InclusionExclusion](../_terms.md#approachinclusionexclusion)
     (картинка — полоска) и новый [approach::VennDiagram](../_terms.md#approachvenndiagram)
     (картинка — диаграмма). Ничего не потеряно — обе картинки остались, каждая при своём подходе.
  2. Ни один подход не нёс поля `Source:` — только у картинок были независимые ссылки. Добавлено
     каждому подходу отдельно от его картинки (см. Requirements). Трассировка: MUST-approach-source.
  3. `euler001.md`/`euler002.md`/`euler003.md` жили как отдельные спеки ВНУТРИ memory-bank —
     конкретные задачи, не переиспользуемое знание. Удалены; их содержимое (там, где оно того
     стоило) свёрнуто в `euler{NNN}/README.md`. Поле `Used in:` у каждого подхода/картинки стало
     настоящей markdown-ссылкой на `README.md` задачи, а не голым текстом. Трассировка:
     MUST-no-task-specifics.
  Трассировка (общая): MUST-one-picture-max, MUST-approach-source, MUST-no-task-specifics.
- **F6** (прямой вопрос пользователя после F5: «здесь же только базовые примитивы, ничего про
  задачу быть не должно, не?»). F5.3 удалила отдельные спеки задач, но оставила в каждом блоке
  строку `Used in: [euler001](...)` — это тоже упоминание конкретной задачи, просто в одну
  строку, и оно же означало, что при удалении/переименовании задачи пришлось бы синхронно править
  ЭТОТ файл — обратный, дублирующий указатель на связь, которая и так целиком видна с другой
  стороны (README задачи явно перечисляет использованные подходы/приёмы). Удалено поле `Used in:`
  из всех записей полностью; связь теперь строго однонаправленная — из задачи в примитив, не
  наоборот. Трассировка: MUST-no-task-specifics (ужесточено), MUST-reuse-not-duplicate
  (переформулировано).

## Architecture

### Обзор (прозой)
Блоки `[approach::*]` в `memory-bank/_terms.md`, по блоку на подход: Essence (одна фраза без
формул) / Recognized by (признаки в условии) / General case (не для конкретных чисел) /
Visualized by + Picture (ровно одна картинка или явное «—» с обоснованием) / Source (независимая
ссылка на стандартность идеи). Ни одного поля про конкретную задачу — ни условия, ни критериев,
ни даже обратной ссылки «где применялось» (см. MUST-no-task-specifics). Каждая запись — либо
атомарная идея, либо явно названная композиция нескольких атомарных (см. Requirements,
MUST-atomic-or-composed). Пополняется при разборе задачи; повторное применение известного
подхода не меняет этот файл вообще — задача в своём README ссылается на уже существующий блок.

### Bounded Contexts и Aggregate Roots
- `approach` — [approach::Collection](../_terms.md#approachcollection) (root): Entry.
- `viz` — соседний контекст, связь через `Visualized by:` ↔ `Approach:`, строго 1:1 или 1:0.

## Requirements
> Формулировка — критерий приёмки — статус.

### MUST
- Каждая запись MUST содержать поля Essence / Recognized by / General case / Visualized by /
  Source (плюс `Picture:`, когда есть картинка), MUST NOT содержать поле про конкретную задачу
  — **MUST-entry-schema** — критерий: `grep` по каждому обязательному заголовку поля даёт
  столько же строк, сколько записей (6); поля `Used in:` в файле нет вообще. Статус: реализовано.
- «Суть» MUST быть одной фразой без формул — **MUST-essence-plain** — критерий: в поле нет `·`,
  `/`, степеней, обозначений переменных. Статус: реализовано.
- «Общий случай» MUST описывать идею для произвольных параметров, MUST NOT выдавать частный
  случай за общий — **MUST-general-case** — критерий: для включения-исключения назван случай k
  условий, «А+Б−АБ» помечен как k=2. Статус: реализовано.
- «Когда узнаётся» MUST называть признаки в ТЕКСТЕ УСЛОВИЯ, по которым подход виден до решения —
  **MUST-recognition-trigger** — критерий: признак формулируется как наблюдение над условием
  («в условии есть "или"», «нужна сумма, а не количество»), не как свойство решения. Статус:
  реализовано.
- Поле `Visualized by` MUST ссылаться РОВНО НА ОДИН блок `[viz::*]`, MUST NOT — на несколько —
  **MUST-one-picture-max** — критерий: `grep` числа `[viz::` внутри одной записи `Visualized by:`
  не больше одного. Идея, у которой стандартно есть 2+ независимых визуальных формы, разводится
  на 2+ отдельные записи подхода (см. F5.1), а не собирает несколько картинок в одну запись.
  Статус: реализовано (InclusionExclusion/VennDiagram разведены).
- Поле `Visualized by` MUST сопровождаться полем `Picture:` со встроенной картинкой (той же, что
  у блока `[viz::*]`), не только текстовой ссылкой — **MUST-inline-picture** — критерий: у блока
  подхода в `_terms.md` есть markdown-image, ведущий на `visualizations/build/<slug>.png` — для
  каждой записи, у которой картинка вообще есть. Статус: реализовано.
- Каждая запись MUST нести своё собственное поле `Source:` — независимую ссылку на то, что идея
  стандартна, ОТДЕЛЬНУЮ от `Source:` её картинки (пусть даже совпадающую по факту) —
  **MUST-approach-source** — критерий: `grep -A1 '^Visualized by\|^Picture' _terms.md` — сразу
  после блока подхода есть строка `Source:`, не только у `[viz::*]`-блока. Статус: реализовано
  (все 6 записей).
- Блок-агрегат `[approach::Collection]` MUST NOT нести собственную встроенную картинку/галерею —
  **MUST-no-aggregate-picture** — критерий: у него нет `Picture:`/`Gallery:` поля; та же картинка
  уже встроена в конкретную запись подхода на пару абзацев ниже, третья копия — не находка, а
  дублирование (прецедент: галерея была добавлена и убрана в этой же сессии). Статус: реализовано.
- Поле `Visualized by` MUST ссылаться на конкретные блоки `[viz::*]` (не на сам
  [viz::Catalog](../_terms.md#vizcatalog) — тот аггрегат, не отдельная картинка); значение «—» MUST
  трактоваться как сигнал завести картинку, если он в принципе возможен, а не постоянное
  состояние по умолчанию — **MUST-visualized-by** — критерий: у каждой записи ровно одна ссылка
  либо явный «—» с обоснованием, почему картинки, видимо, не будет. Статус: реализовано (5 из 6
  подходов имеют картинки; `Precomputation` — обоснованное «—»).
- Наличие или отсутствие картинки у подхода MUST NOT решать, заводить ли для него отдельную
  ЗАПИСЬ подхода — это два разных вопроса: «узнаётся ли эта идея отдельно от соседних» (решает
  запись) и «есть ли у неё устоявшийся визуальный образ» (решает картинку) —
  **MUST-approach-independent-of-picture** — критерий: `[approach::Precomputation]` — легитимная
  отдельная запись без `Picture:`, рядом с `[approach::BinarySearch]`, у которого картинка есть;
  обе идеи узнаются в задачах порознь. Статус: реализовано (найдено и исправлено после прямого
  вопроса пользователя — F4).
- Подход MUST NOT заводиться под существующую картинку ради симметрии — **MUST-no-invented-approach**
  — критерий: картинка без подхода помечается на своей стороне (`Approach: —` с причиной), в
  коллекции записи нет. Статус: реализовано (skip counting).
- Связь с картинками MUST быть двусторонней: `Visualized by:` ↔ `Approach:` —
  **MUST-bidirectional-link** — критерий: множество ссылок в одну сторону совпадает с множеством в
  другую. Статус: реализовано.
- Каждая запись MUST быть либо атомарной (одна неделимая идея), либо явно названной композицией
  из 2+ атомарных идей, использованных вместе — MUST NOT быть «атомарная идея + недоназванный
  довесок» — **MUST-atomic-or-composed** — критерий: если решение реально использует 2+
  независимо стандартные идеи, каждая получает свою запись (как `Precomputation`+`BinarySearch`,
  `InclusionExclusion`+`VennDiagram`), а не одну составную запись с двумя картинками или одну
  запись, тихо описывающую только половину происходящего. Статус: реализовано (обе находки F4/F5
  — примеры исправления именно этого нарушения).
- Коллекция MUST NOT хранить НИЧЕГО о конкретной задаче — ни условие, ни решение, ни критерии
  корректности, ни даже обратную ссылку «использовано в» — **MUST-no-task-specifics** — критерий:
  в `memory-bank/` нет файлов `specs/euler{NNN}.md`, блоков `[euler::*]` и поля `Used in:`;
  `grep -c '^Used in:' _terms.md` равен нулю. Связь однонаправленная: задача в своём README
  ссылается на блок здесь по имени (`../memory-bank/_terms.md#approachname`), не наоборот —
  хранить факт связи в двух местах означало бы синхронизировать их при каждом переименовании или
  удалении задачи. Статус: реализовано (найдено в два приёма — сначала спеки задач, потом и само
  поле `Used in:`, F5→F6).
- Повторное применение известного подхода к новой задаче MUST NOT менять этот файл — MUST
  ссылаться на существующий блок из README самой задачи — **MUST-reuse-not-duplicate** —
  критерий: `git diff` на `_terms.md` пуст при добавлении задачи, повторно использующей уже
  описанный подход; ссылка появляется только в `euler{NNN}/README.md`. Статус: реализовано.

### SHALL
- При добавлении записи в один из двух списков (подходы / картинки) SHALL проверяться второй и
  обновляться ссылка там же — **SHALL-cross-update**. Статус: процессное, PASSIVE
  (`.claude/rules/visualization-principles.md`, принцип 9).

### SHOULD
- Название подхода SHOULD быть общепринятым (проверенным поиском), как и у картинок —
  **SHOULD-standard-name**. Статус: реализовано для всех шести (каждое название сверено поиском
  до записи).

## Связи
- Файл коллекции: блоки `[approach::*]` в `memory-bank/_terms.md`.
- Соседний спек: [visualizations](visualizations.md) (картинки для каждого подхода).
- Правила: `.claude/rules/visualization-principles.md`, принципы 9 (двусторонняя связь), 11
  (атом/композиция, 1 подход = 1 картинка), 12 (задачи не хранятся в memory-bank).
- Не путать: `TRICKS.md` (корень репозитория), CLAUDE.md «Communication style».
